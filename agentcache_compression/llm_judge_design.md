# LLM-as-a-Judge: Code Quality Evaluation for the Multi-Turn Benchmark

**Status:** Design doc — implementation (`judge_multi_turn.py`) not yet built.
**Attaches to:** §6.1 Multi-Turn Conversation evaluation in `usenix.tex`.
**Data required:** Qwen-7B pairs judgeable from disk today; GPT-OSS-20B requires
a benchmark rerun after a Harmony-channel fix (see §3.3).

---

## 1. Why we are doing this

AgentCache's central claim is that centroid KV injection reduces cold-start TTFT
(1.49× mean speedup on Qwen-7B, 1.80× on GPT-OSS-20B in the multi-turn benchmark)
**without degrading what the model produces**. The first half of that claim is
well-measured. The second half currently rests on three proxy metrics, none of
which can detect a semantic regression in generated code:

| Existing metric | Where | What it actually measures | Why it is insufficient |
|---|---|---|---|
| ROUGE-L vs cold baseline | `analyze_multi_turn.py` (lines ~321–380), `LMCacheCentroidN256.ipynb` cell 13 | Textual overlap with the baseline response | See divergence problem below |
| Coherence heuristic | `test_compression.py:104` (`check_coherent`) | ≥20 words, no token repeated in >40% of the last 30 words | Only catches catastrophic degeneration/looping; fluent-but-wrong code passes |
| Keyword task check | `test_compression.py:118` (`check_task`), keywords auto-generated by `prepare_data.py` | Response contains ≥1 keyword from any `must_include_any` group | Surface matching; a response that *mentions* `argparse` but contains broken code passes |

**The divergence problem.** The paper has two distinct configurations, and ROUGE-L
only works for one of them:

- **§6.2 (LMCache+Centroid, T4):** the centroid is injected *in front of* the full
  system prompt, temperature is 0, so outputs are byte-identical to baseline.
  ROUGE-L = 1.0 is correct and meaningful there — but it is the *easy* case. It
  proves determinism was preserved, not that compression preserves quality.
- **§6.1 (multi-turn, Blackwell):** the synthetic mode **removes the system prompt
  entirely** and replaces it with the centroid (`prompt = [pad]*N + user tokens`).
  Outputs legitimately differ from the cold baseline by construction. ROUGE-L drops
  below 1.0 and fundamentally cannot distinguish *"different wording, equally good
  code"* from *"degraded code."* This is the hard case, and it is exactly where the
  paper's speedup numbers come from.

The LLM-as-judge evaluation closes this gap. It converts the open question
*"did the speedup cost us quality?"* into a reportable **win/tie/loss rate**
against the cold baseline — the standard methodology for comparing free-form
generations when no executable ground truth exists (and our eval tasks have no
unit tests to run).

## 2. Which experiment this attaches to

**The multi-turn conversation benchmark (§6.1 of the paper).**

- 10-turn CSV-CLI Python coding conversation; each turn's response becomes part of
  the next turn's history.
- ~2000-token system prompt (`prompts/2000_python_agent_system.txt`).
- NVIDIA Blackwell GPU; generated by `multi_turn_benchmark.py` via
  `run_multi_turn_pipeline.py`.
- Five modes per model: `cold`, `warm_apc`, `synthetic` N ∈ {64, 128, 256}.

It does **not** attach to §6.2 (LMCache+Centroid): in that configuration outputs
are byte-identical to baseline (ROUGE-L 1.0 at temperature 0), so a judge would
return 100% ties and add nothing.

### Source data (verified on disk, 2026-06-06)

| File | Model | Records | Modes | Notes |
|---|---|---|---|---|
| `agentcache_compression/results/qwen7b.jsonl` | Qwen-2.5-7B | 50 = 5 modes × 10 turns | cold, warm_apc, synthetic N64/128/256 | Full responses, 1,181–8,412 chars |
| `agentcache_compression/results/gptmulti_turn_benchmark.jsonl` | GPT-OSS-20B | 50 = 5 modes × 10 turns | same | **Unusable for quality eval — Harmony-channel feedback bug degenerates later turns in all modes; rerun required** (see §3.3) |

Both files store, per record: `mode`, `N`, `turn`, `conversation_id`, the turn's
`user` question, and the complete `response` text. All generations were produced
at `temperature=0.0` with a dedicated full-generation call separate from the
`max_tokens=1` TTFT measurement (`multi_turn_benchmark.py`), so the stored

The Qwen-1B raw JSONL (`nogb_csv_cli_2048withcachehitbenchmark.jsonl`) was never
committed — its numbers exist only in `results/ttft_comparison.png`. Judgeable
models are therefore **Qwen-7B and GPT-OSS-20B only**; the paper must scope the
quality claim accordingly.

## 3. Inputs: pair construction

### 3.1 Pairing rule

For each model and each turn `t ∈ {1..10}`:

```
reference  = response of mode "cold"       at turn t   (full system prompt, full prefill)
candidate  = response of mode "synthetic"  at turn t   (system prompt removed, centroid N injected)
```

One pair per N value: **10 turns × 3 N values × 2 models = 60 pairs.**

`warm_apc` is excluded: it uses the same prompt text as `cold` at temperature 0,
so its responses carry no additional information for a quality comparison.

### 3.2 What the judge sees per call

For a pair at turn `t`, the judge sees **each condition's own transcript up to
and including turn t**, reconstructed from the per-turn `user`/`response` fields
in the JSONL:

```
Conversation A:  user_1, assistant_A_1, ..., user_t, assistant_A_t
Conversation B:  user_1, assistant_B_1, ..., user_t, assistant_B_t
```

and is asked to compare **only the final assistant response of each transcript**,
using the prior messages purely as context. This is required, not optional: the
benchmark conversation is heavily anaphoric — turns 2–10 are all of the form
*"Add a --filter flag…"*, *"Refactor the summary logic into a standalone
summarize(df) function… Update run()…"* — so the current question alone is
under-specified for 9 of the 10 turns. A judge shown only the turn-t question
would produce false losses/ties against responses that correctly modify code
established in earlier turns.

The A/B assignment is **randomized per pair** using a fixed, recorded RNG seed,
so position bias cannot systematically favor either condition and every verdict
can be de-anonymized afterward. The protocol is symmetric: each side is judged
with its *own* history, and neither side ever sees the other's history.

The judge does **not** see: which transcript is which condition, the system
prompt, TTFT numbers, or mode names.

**Cost note:** at turn 10 a call carries two near-full transcripts (responses run
up to ~18K chars each), so late-turn calls can reach tens of thousands of tokens.
With ≤60 pairs total this is cheap in absolute terms, but the script should
support truncating *earlier assistant turns* (never the final response or any
user turn) if a context limit is ever hit, and must record when it does so.

### 3.3 Mandatory data hygiene (do this before judging)

**The GPT-OSS-20B run must be rerun before judging — its stored data is unusable
for quality evaluation.** Survey of `gptmulti_turn_benchmark.jsonl` (2026-06-06):

| Mode | Healthy turns | Degenerate turns |
|---|---|---|
| cold | 2–5 (turn 1 salvageable, see below) | 6–10 |
| warm_apc | 1–2 | 3–10 |
| synthetic N=64 | 1–4 | 5–10 |
| synthetic N=128 | 1–9 | 10 |
| synthetic N=256 | intermittent | 2, 4, 7, 10 |

Root cause (`multi_turn_benchmark.py:44`, `build_messages`): GPT-OSS emits
Harmony channel text, and the benchmark stores and feeds back the **raw
concatenation of all channels** (`analysis…assistantfinal…`) as the assistant
history message. The chat template expects final-channel content only, so the
history becomes progressively malformed and the model degenerates as turns
accumulate — in *all* modes, including cold (i.e. a benchmark formatting bug,
not a centroid bug). The degenerate responses are long (9–15K chars), so length
filters do not catch them, and `check_coherent`'s last-30-words repetition test
misses several.

Required fixes before the judge can run on GPT-OSS:

1. **Patch the benchmark** to strip responses to the final channel before storing
   and before appending to history: `resp.split("assistantfinal")[-1]` (fall back
   to the raw text when the marker is absent, as for non-Harmony models).
2. **Rerun the full GPT-OSS multi-turn benchmark** with the patch. Only 6/50
   stored records contain an `assistantfinal` marker, so the existing file is not
   salvageable by post-processing (the cold turn-1 record is — its final channel
   contains a complete, correct answer — but turns without the marker are pure
   degeneration with nothing to extract).
3. **Pre-pass sanity filter on the new data:** manually inspect every reference
   response (10 cold responses per model — cheap) rather than trusting
   `check_coherent`, which provably misses this failure mode.

`qwen7b.jsonl` was surveyed the same way and is fully clean — Qwen-7B pairs can
be judged from the existing file with no rerun.

This also affects the paper beyond the judge: the GPT-20B TTFT numbers in §6.1
came from this same run. The TTFT measurement is a separate `max_tokens=1` call,
so the timings are likely valid, but the conversation histories that grew across
turns contained garbage text — the rerun should confirm the 1.80× figure holds
with well-formed conversations.

### 3.4 The multi-turn subtlety (and how we frame it)

At turn `t > 1`, each mode's response depends on **its own** accumulated history:
cold saw its own turns 1..t−1, synthetic saw its own. The two responses at turn t
are therefore not same-context counterfactuals.

This is not a flaw — it is the realistic end-to-end comparison: we are judging
**the quality of the conversation each system actually produced**, which is what a
user of the deployed system experiences. The transcript-based protocol in §3.2
matches this framing exactly: each final response is evaluated in the context of
its own conversation, the same way a user would experience it. The paper must
state this framing explicitly: we measure *full-conversation* quality at each
turn, not standalone answer quality on identical contexts.

Two consequences for the judge:

- The judge must not penalize conversation A's final response for differences in
  conversation B's *earlier* turns (or vice versa) — earlier turns are context,
  not the object of judgment. This is enforced in the system prompt (§5).
- Because both transcripts are shown symmetrically, neither condition gains an
  information advantage, and condition identity is not leaked beyond whatever the
  response texts themselves reveal.

A rejected alternative — showing only the current turn's question — would have
been cheaper but is broken for this benchmark: the turns are anaphoric (§3.2),
so a current-turn-only judge measures standalone answer quality on
under-specified questions, which is both weaker and misleading for turns 2–10.

## 4. Judge configuration

- **Judge model:** an OpenAI hosted model (e.g. the current flagship GPT model at
  time of running), called through the `openai` Python client already used
  throughout this repo (`multi_turn_benchmark.py` uses it against the local vLLM
  endpoint; the judge simply points at the OpenAI API instead).
- **Temperature 0**, structured/JSON output mode, fixed `seed` parameter if the
  endpoint supports it.
- **Pin and record the exact judge model snapshot** (e.g. a dated model id) in the
  output file — "the judge" must be reproducible and citable in the paper.

**Self-preference caveat.** One of the two models under test (GPT-OSS-20B) is
OpenAI-family, and LLM judges show measurable self-preference bias. Mitigations,
in order of increasing effort:

1. Always report win/tie/loss **per model under test** — never pooled — so any
   GPT-family inflation is visible in isolation.
2. Both sides of every pair come from the *same* model under test (cold vs
   synthetic Qwen-7B; cold vs synthetic GPT-20B), so self-preference toward a
   family cannot favor one *condition* over the other — it can at most compress
   verdicts toward "tie" for the GPT-20B pairs. This is the key structural defense
   and should be stated in the paper.
3. Optional robustness check: re-run a sample (or all 60 pairs — it is cheap) with
   a second judge from a different family and report agreement (e.g. Cohen's κ).

## 5. Judge system prompt (full text)

The user message per call contains the task and the two responses; the system
prompt below defines the rubric. **This exact text should be published in the
paper's appendix.**

```text
You are a senior Python engineer serving as an impartial judge. You will be shown
two transcripts of the same multi-turn coding conversation, labeled A and B. Both
transcripts contain the same user requests, but the assistant responses differ.
Your job is to compare ONLY the final assistant response in each transcript — the
answer to the last user request — and decide which one better serves the user,
or whether they are equivalent in quality.

Use the earlier turns of each transcript purely as context for understanding what
the final request refers to (e.g. "add a flag to the script" refers to code built
up in that transcript's earlier turns). Judge each final response against its OWN
transcript's history. Do not penalize a final response because the two transcripts
diverged in earlier turns, and do not judge the quality of earlier responses —
they are context, not the object of evaluation.

Evaluate the two final responses on these four dimensions, in this order of
importance:

1. correctness — Would the code run as written and do what the user asked?
   Look for bugs, wrong APIs, logic errors, and code that would raise exceptions
   on the described inputs. For a modification request, correctness includes
   correctly integrating with the code established earlier in that transcript.
2. completeness — Does the response address every part of the final request? A
   request may contain multiple requirements (e.g. read a file AND print a
   summary AND handle a specific column type).
3. code_quality — Is the code idiomatic, readable, and reasonably robust
   (sensible names, appropriate error handling, no needless complexity)?
4. instruction_adherence — Does the response follow explicit constraints stated
   in the request (e.g. "use argparse", "name the entry point function run()",
   "apply --sample before filtering")?

Rules:
- For each dimension, and for the overall verdict, answer exactly one of:
  "A", "B", or "tie".
- "tie" is a normal, expected outcome. If both responses would satisfy the user
  about equally well on a dimension, say "tie". Do not invent a preference.
- Judge the substance of the code, not its presentation. Do NOT reward a response
  for being longer, having more prose, more headers, or more bullet points.
  Extra explanation is neither a bonus nor a penalty unless the user asked for it.
- Do NOT let the order of presentation influence you. A and B were assigned
  randomly.
- If one response is incoherent, off-topic, or degenerate (repeated text, markup
  garbage), it loses every dimension it fails on.
- Base your judgment only on the transcripts shown. Do not assume hidden context.

Output strictly the following JSON object and nothing else:

{
  "correctness": "A" | "B" | "tie",
  "completeness": "A" | "B" | "tie",
  "code_quality": "A" | "B" | "tie",
  "instruction_adherence": "A" | "B" | "tie",
  "overall": "A" | "B" | "tie",
  "reason": "<one sentence justifying the overall verdict>"
}
```

User message template per pair (transcripts reconstructed from each mode's
per-turn `user`/`response` fields, turns 1..t):

```text
## Conversation A (turns 1-{t})

[user 1]: {user_1}
[assistant A]: {response_a_1}
...
[user {t}]: {user_t}
[assistant A — FINAL RESPONSE TO JUDGE]: {response_a_t}

## Conversation B (turns 1-{t})

[user 1]: {user_1}
[assistant B]: {response_b_1}
...
[user {t}]: {user_t}
[assistant B — FINAL RESPONSE TO JUDGE]: {response_b_t}
```

## 6. Outputs and aggregation (spec for `judge_multi_turn.py`)

The future implementation lives at `agentcache_compression/judge_multi_turn.py`
and follows the repo's existing pattern: a benchmark-style script that appends
JSONL, plus analysis that mirrors `analyze_multi_turn.py`.

**Per-pair record** → `agentcache_compression/results/judge_verdicts.jsonl`:

```json
{
  "model_under_test": "qwen7b",
  "turn": 3,
  "N": 128,
  "a_is": "cold",
  "seed": 42,
  "judge_model": "<pinned model id>",
  "verdict": { "correctness": "tie", "...": "...", "overall": "tie", "reason": "..." },
  "synthetic_result": "win" | "tie" | "loss"
}
```

(`synthetic_result` is the de-anonymized overall verdict from the synthetic
condition's perspective — the quantity the paper reports.)

**Summary tables** (printed + saved as a figure, matching the per-turn style of
`analyze_multi_turn.py`):

1. Win/tie/loss for synthetic vs cold, per **model × N**, overall verdict.
2. The same broken down per **rubric dimension** — this is what localizes a
   regression (e.g. "losses concentrate in instruction_adherence").
3. **Per-turn** win/tie/loss — does quality hold as conversation history grows?
   This mirrors the per-turn TTFT plots and lets the paper present latency and
   quality on the same x-axis.

## 7. What the results will mean for the paper

The judge results land in the consolidated **Model Quality** subsection of
§Evaluation, alongside the existing metrics, giving three tiers of evidence:

| Configuration | Quality evidence |
|---|---|
| §6.2 injection-in-front (LMCache+Centroid, T4) | ROUGE-L 1.0 — output *identity* preserved |
| §6.1 compression mode (multi-turn, Blackwell) | coherence + task-check (existing) **+ judge win/tie/loss (new)** — output *quality* preserved despite different text |

Interpretation of the possible outcomes:

- **Mostly ties / balanced wins** (the hypothesis): centroid compression preserves
  answer quality, so the 1.49×/1.80× speedups are effectively free. This directly
  strengthens the paper's central claim and pre-empts the obvious reviewer
  objection ("ROUGE-L can't show quality in the compression setting").
- **Synthetic losses concentrated in `correctness`:** there *is* a quality cost.
  The paper must then report the trade-off honestly — speedup vs win-rate per N
  becomes a figure, and the claim softens from "free speedup" to "tunable
  latency/quality trade-off."
- **Losses concentrated in `instruction_adherence`:** the centroid encodes the
  system prompt's *domain* but loses its *behavioral constraints*. This connects
  to the GOODBYE behavioral-encoding analysis (internal; HANDOFF §8.2) and points
  at training-data fixes rather than architecture fixes.
- **Losses growing with turn number:** centroid quality degrades as history grows —
  important deployment caveat, and it shares an x-axis with the per-turn TTFT
  story, so the paper can show exactly where the method stops being free.
- **Losses shrinking as N grows (64 → 128 → 256):** strengthens the N-ablation
  narrative. TTFT is flat in N above a floor, so quality becomes the *reason* to
  choose larger N — turning the ablation from "N doesn't matter" into "N buys
  quality at no latency cost."

## 8. Limitations and threats to validity

State these in the paper rather than letting a reviewer find them:

1. **Sample size.** 60 pairs (30 judgeable today from Qwen-7B; the GPT-20B 30
   require the §3.3 rerun), one conversation per model. Report raw win/tie/loss
   counts with ties explicit; do not collapse ties into wins. Avoid strong
   statistical claims.
   Cheap extension path: the 25-task single-turn N-ablation sets
   (`results/gptoss64.jsonl`, `gpt128.jsonl`, `gpt256.jsonl`) already contain
   synthetic outputs and would roughly double n — but they need a matching cold
   GPT-OSS run of the same 25 tasks to form pairs.
2. **Judge bias.** Position bias (mitigated by per-pair randomization with a
   recorded seed), verbosity bias (mitigated by explicit length-blind
   instructions), self-preference (mitigated structurally — both sides of every
   pair come from the same model under test — plus per-model reporting and an
   optional second-family judge agreement check).
3. **Not an execution-based metric.** The judge reads code; it does not run it.
   A complementary objective check (extract fenced code blocks, `ast.parse`, smoke
   execution) would be stronger evidence for `correctness` specifically and is a
   natural follow-up, but is out of scope for this design.
4. **Divergent histories.** Turn-t pairs compare conversations that diverged at
   turn 1 (§3.4). Framed as end-to-end system comparison: the judge sees both
   transcripts symmetrically and evaluates each final response in its own
   conversation's context. The paper must state that this measures
   full-conversation quality, not standalone answer quality on identical
   contexts. A secondary effect: a weak earlier answer in one transcript can make
   a *correct* continuation of it look worse — this is a property of the system
   being measured, not a judging error, but reviewers should see the per-turn
   breakdown (§6) to spot compounding effects.
5. **Reproducibility.** Pin the judge model snapshot, temperature 0, record the
   randomization seed in every verdict record, and publish the system prompt
   (§5) in the paper appendix.
